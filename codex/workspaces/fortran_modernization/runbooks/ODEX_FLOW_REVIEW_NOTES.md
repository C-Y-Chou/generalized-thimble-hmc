# ODEX / Flow Review Notes

Updated: 2026-05-09
Scope: reference-backed review notes plus current source policy for behavior-preserving Fortran modernization. No production job submission.

## Purpose

This note fixes the first low-level algorithm review boundary: the ODE flow integrator used by TLTM. The goal is not to improve the physics or tune numerical behavior yet. The goal is to identify what current code implements, what reference algorithm it should be compared against, and what must be baselined before any refactor.

## Reference Definition

Primary reference:

- Hairer, Norsett, Wanner, Solving Ordinary Differential Equations I, Section II.9, Extrapolation Methods.
- Hairer ODEX appendix: `SUBROUTINE ODEX`, described as an extrapolation code for `y'=f(x,y)`, based on the GBS algorithm, with variable order, variable step size, and optional dense output.

Reference features relevant to TLTM:

- Basic integrator is the explicit midpoint / Gragg-Bulirsch-Stoer style construction.
- A large step `H` is subdivided by a sequence `n_1, n_2, ...`; each row builds a midpoint approximation with `h_i = H / n_i`.
- Extrapolation is in even powers, with Aitken-Neville style denominators based on `(n_i / n_j)^2 - 1`.
- Error estimates come from differences between extrapolation levels.
- Step size and order are adapted using work estimates and safety factors. The ODEX appendix names defaults including safety factors around `0.65` and `0.94`/`0.90`, with order-change thresholds around `0.8`/`0.9`.
- ODEX supports dense output, but TLTM appears to require endpoint flow values rather than dense interpolation. Lack of dense output is therefore a design difference, not automatically a bug.

## Current Implementation Map

Primary implementation file:

- `src/physics/solve_flow.f90`

ODEX-like core:

- `odex_step`: constructs midpoint rows, applies endpoint smoothing, builds the extrapolation table, estimates error, and proposes the next step/order.
- `ensure_odex_tables`: builds cached step counts, inverse exponents, and extrapolation denominators.
- `build_nsteps`: defines the current subdivision sequence.
- `calculate_wk`, `calculate_hk`, `calculate_ak`: work and step-size/order selection helpers.
- `intode`: endpoint integration driver, acceptance loop, failure handling entry point, and context-aware diagnostics.

Flow-facing public layer:

- `flowz`: maps real state to complex flow endpoint.
- `flowzr`: inverse-like flow by integrating with negated RHS scale.
- `flow`: integrates flow plus Jacobian-like sensitivity state.
- `rhs_flow_vec`, `rhs_flow_jac`: antiholomorphic flow RHS and Jacobian RHS wrappers around model derivative/Hessian-vector operations.

Non-ODEX policy/status mixed into the same module:

- Solver-internal residual assist for NT/QN residual-evaluation contexts.
- Strict final-proposal flow gates.
- Strict mode, tracing, fallback counters, failure snapshot capture, and diagnostics.
- Historical note: Radau5, fixed/chunked Radau, JFNK rescue, and Radau replay diagnostics were deleted from active source on 2026-05-09.

This file is therefore not just an ODEX implementation. It is currently an integration engine plus flow mapping plus failure policy plus diagnostics.

## Initial Correspondence To Hairer ODEX

Observed matches:

- The code uses explicit-midpoint style internal rows and extrapolates in even powers.
- The extrapolation denominator cache has the expected `(n_i / n_j)^2 - 1` structure.
- Error estimation uses a scaled RMS norm with absolute/relative tolerance terms.
- Step size and order adaptation are present, with constants matching the ODEX family closely enough to treat this as an ODEX-derived implementation.
- Invalid RHS values are handled explicitly and routed into smaller steps or fallback policy.

Observed differences or review items:

- The step-number sequence currently generated by `build_nsteps` appears to be `2, 4, 6, 12, 18, 36, ...`. This differs from common ODEX defaults such as even sequences `2, 4, 6, 8, 10, ...` or other Hairer-supported sequences. This must be treated as behavior, not corrected without regression evidence.
- `odex_k_min = 4` and `odex_k_max = 10` are project-specific behavior. Changing these changes trajectory, fallback frequency, and performance.
- Dense output is absent or unused. This is likely acceptable for endpoint-only TLTM flow, but it should be documented as a deliberate scope difference.
- The integration driver contains residual-assist/final-flow policy that is outside the mathematical ODEX core. Refactoring must separate mechanism from policy without changing when each policy fires.

## Behavior Preservation Risks

High-risk behavior surfaces:

- Step-number sequence, order bounds, safety factors, and error exponent formulas.
- Absolute/relative tolerance scaling and tolerance floors.
- `h_min` calculation and h-min failure classification.
- Transition order among ODEX retry, solver-internal residual assist, strict final-flow failure, and diagnostics/counters.
- Context-dependent behavior through `intode_current_context` and stage/fallback reason codes.
- Module-level `save` work arrays and counters. These are performance-friendly but create reentrancy and concurrency risk if the project later moves toward OpenMP/thread-safe execution.
- `flowzr` semantics: inverse flow is implemented by negating the RHS scale while integrating over positive flow time. Any API cleanup must preserve this exactly.
- Failure snapshot and diagnostic APIs, because Stage3_4 troubleshooting may depend on their current behavior.

## Required Baselines Before Refactor

Minimal ODEX/flow regression baselines:

- Fixed-input endpoint regression for `flowz`, `flowzr`, and `flow` on representative configurations.
- Round-trip checks such as `flowz` followed by `flowzr` on known non-singular samples, with current tolerances recorded before modernization.
- Jacobian consistency checks for `flow`: compare returned sensitivity behavior against finite-difference perturbations on small cases.
- RHS mapping checks: real/complex mapping, conjugation convention, and inverse-flow sign convention.
- Failure-path baselines using stored failure snapshots where available: ODEX fail, residual-assist success/failure, strict final-flow rejection, and strict-mode behavior.
- Counter/diagnostic baselines: fallback counters, context counters, last-failure metadata, and trace lengths for at least one known failure case.
- Performance baselines: accepted/rejected step counts and wall-time envelope on representative short runs. Exact timing need not be bitwise stable, but large drift must be visible.

Recommended baseline outputs:

- A small deterministic flow regression fixture.
- A failure-path replay fixture using current ODEX/assist diagnostic APIs. Historical `run_intode_last_failure_radau_sweep` was deleted with the Radau rescue source.
- A text/JSON summary of endpoint values, error flags, fallback counters, and step/failure metadata.

## Refactorability Assessment

Safe now, as planning work:

- Document ODEX mechanism vs TLTM flow policy boundaries.
- Build a baseline matrix and identify existing entry points for future tests.
- Review naming, comments, and API boundaries without editing source.
- Classify which subroutines are pure numerical mechanism and which are production failure policy.

Potentially safe after baselines exist:

- Extract ODEX table/cache construction into a clearer internal unit while preserving exact constants and sequence.
- Separate flow wrappers from integration driver policy at module level, if public interfaces and diagnostics remain stable.
- Rename local variables or introduce derived types only if bitwise/near-bitwise behavior is verified.
- Add non-invasive tests around existing APIs before any implementation refactor.

Blocked until Stage3_4 jobs complete or explicit approval is given:

- Changing step-number sequence, `odex_k_min`, `odex_k_max`, safety constants, or error exponents.
- Changing `h_min`, tolerance floors, residual-assist policy, or strict final-flow policy.
- Reintroducing or replacing secondary-integrator rescue without a new explicit decision.
- Removing or altering diagnostic counters used by current production debugging.
- Any performance optimization that changes accepted step sequence, fallback frequency, or endpoint values without a recorded baseline comparison.
