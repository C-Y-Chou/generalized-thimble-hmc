# M6 Reference Dataset Readback Plan

Updated: 2026-05-10 JST

Scope: define the manual and future-automated checks used by the modernization workstream to accept a generated or curated dataset/package as a behavior-preservation reference.

This plan does not implement a reader yet. It defines what the reader/checklist must verify before source-code modernization resumes.

## Readback Philosophy

The modernization reference dataset/package is not the final physics dataset. It is a protection layer for future refactors.

Stage3_4 is used here as design context, not as a required result source. A reference dataset may be generated by modernization itself as long as it matches the intended workflow context and records enough provenance.

Readback therefore asks:

- Can we identify exactly what code/config/protocol produced this package?
- Can we compare future code against it without private memory?
- Can we tell whether a future change preserved physics behavior or changed interpretation?
- Can we distinguish local guardrail artifacts from reference-grade modernization baselines?

## Manual Readback Sequence

1. Locate package root and manifest.
2. Confirm package class is accepted for modernization use.
3. Verify source branch, commit, dirty status, config digests, and seed policy.
4. Confirm physical point and method mapping.
5. Verify `nofb` and `withfb` matched-seed structure where required.
6. Verify v0 compatibility outputs exist and are parseable.
7. Verify v1alpha sidecars exist when declared.
8. Verify protocol audit verdicts and sidecar readback.
9. Verify merged per-seed summaries preserve required provenance columns.
10. Verify aggregate/evaluation summaries record physical observables and diagnostics.
11. Record caveats and decide whether the package is accepted, accepted-with-caveats, or rejected.

## Minimum Required Checks

### Provenance

- `source_commit` resolves to an intended TLTM commit.
- `source_dirty_status` is clean, or dirty files are explicitly listed and archived.
- Config files and digests are present.
- Env overrides and QN/flow/reverse-gate policy ids are present.

### Method Pairing

- `no_fb` and the canonical `withfb` method are both present when the reference is meant to protect the Stage3_4-style comparison.
- Method names are mapped to scientific labels in the manifest.
- Seed policy is matched across methods, or differences are explicitly documented.

### Protocol

- Tempering protocol id matches the selected convention.
- Measurement boundary is `post_swap`.
- Label trace boundary is `post_swap`.
- Invalid swap/reflow behavior is recorded as rejection without state mutation.

### Sidecars And Audit

- If `v1_sidecars_present == true`, every included seed/chunk has manifest/protocol sidecar paths or a merge-preserved summary.
- Protocol audit status is `pass` for accepted packages.
- Audit warnings are recorded and reviewed.

### Physics/Diagnostics Summary

The readback note should summarize at minimum:

- phase/observable estimates for the reference task;
- acceptance rates;
- reverse-gate candidate/pass/reject counts;
- proposal construction failure counts;
- ODE/final-flow failure status counts;
- Newton/QN residual and solver-assist counters;
- runtime and known anomaly notes.

## Acceptance States

- `accepted`: usable as a modernization reference baseline.
- `accepted_with_caveats`: usable only for specified refactor scopes; caveats must be listed.
- `rejected`: not usable as a modernization reference baseline.
- `legacy_only`: kept for historical comparison but not used to accept future behavior-preserving refactors.

## Future Automation Design

A future readback helper may be added after this planning gate. It should be read-only and should not submit jobs.

Proposed behavior:

```text
read manifest -> verify required fields -> check paths -> parse merged summaries
-> check protocol audit summary -> check method/seed pairing
-> emit readback report -> append optional state registry row
```

The first implementation should prefer fail-closed behavior:

- missing required field: fail;
- unresolved path: fail unless archived/offline path is explicitly marked;
- audit error: fail;
- ambiguous method mapping: fail;
- missing physical point: fail.

## Readback Output

Each accepted or rejected package should produce:

- a package-specific readback note;
- a row in `state/M6_REFERENCE_PACKAGES.tsv`;
- a short status update in `runbooks/STATUS.md`;
- a list of allowed refactor scopes protected by this package.

## Stop-For-Decision Conditions

Stop for user decision if:

- the proposed reference class lacks matched method/seed structure but is intended to protect `nofb` vs `withfb` behavior;
- `withfb` method naming differs from current `fb_norefine` mapping;
- protocol timing differs from post-swap convention;
- physical observables disagree with the intended reference interpretation;
- package is large/costly to rebuild and readback cannot prove provenance;
- accepting the package would constrain future RNG/state/schema work in a non-obvious way.
