# M6 Reference Dataset Design Spec

Updated: 2026-05-10 JST

Scope: define the modernization reference dataset/package that will protect future code-refine work.

This document uses Stage3_4 as a design context, not as a required result source. Modernization does not need to wait for Stage3_4 production outputs before making progress. Stage3_4 tells us what kind of physics task the code is currently serving: `nofb` vs `withfb` at `t=0.35`, `L=2`, `nstep=20`, with TLTM/replica-exchange protocol and p28 fallback policy.

## Boundary

Stage3_4 owns:

- the separate `nofb` vs `withfb` production comparison;
- production queue/chunk strategy;
- production/intermediate output roots;
- workspace rename/reorganization;
- deletion, archival, or relocation of Stage3_4 artifacts;
- final physics interpretation of that comparison.

Fortran modernization owns:

- designing and generating/curating reference datasets for future refactors;
- deciding what reference scale is sufficient for each refactor class;
- recording the reference baseline as a modernization asset;
- defining readback/audit checks;
- using accepted reference datasets to protect code cleanup, API redesign, state/status work, and wrapper/schema migration.

## Role Of Stage3_4 In This Workstream

Stage3_4 is a reference context:

- It identifies the current high-value workflow the code must support.
- It tells modernization which method pair, physical point, protocol, and diagnostics should be represented in baselines.
- It helps avoid designing artificial toy baselines that do not protect the real TLTM workflow.

Stage3_4 is not a prerequisite result dependency:

- Modernization does not need Stage3_4 outputs to continue all planning, tooling, local guards, docs, or small/medium reference generation.
- A Stage3_4 result may later be compared against modernization baselines, but it is not the only valid reference source.
- The reference dataset can be generated by modernization itself, as long as it is aligned with the Stage3_4 workflow context and has sufficient provenance/readback.

## Reference Target

The modernization reference dataset should align with:

- physical point: `t = 0.35`, `L = 2`, `nstep = 20`;
- comparison: `nofb` vs `withfb`;
- current method mapping: `nofb == no_fb`;
- current `withfb` mapping: canonical fallback-enabled no-post-refine p28 route, currently represented by `fb_norefine` unless the method naming is intentionally updated;
- canonical route: Newton -> p28 QN BTN/backflow rescue residual -> reverse gate -> Metropolis;
- flow policy: ODEX primary integration plus solver-internal residual assist; strict final `flow(...)` for live proposals;
- tempering protocol: `local update -> swap -> measure/history/label trace`;
- reverse gate: enabled as part of proposal definition;
- v0 compatibility outputs: preserved;
- v1alpha sidecars and protocol audit: present for reference-grade runs unless explicitly scoped down.

## Reference Dataset Classes

Accepted package classes:

- `modernization_local_reference`: small fixed-seed reference used for exact-output or route/counter checks.
- `modernization_validation_reference`: 10k -> 50k -> 100k style reference used before refactors that may affect trajectories or diagnostics.
- `stage3_4_context_aligned_reference`: a modernization-built reference aligned with the Stage3_4 production task shape.
- `legacy_characterization_reference`: historical data retained only for comparison, not for accepting new behavior-preserving refactors.

Rejected as reference datasets:

- local smoke artifacts;
- M4 guardrail outputs;
- partial failed chunks without a documented recovery/merge note;
- outputs using an obsolete tempering measurement boundary unless intentionally kept as `legacy_characterization_reference`;
- outputs without method/seed/config provenance.

## Required Artifact Pointers

The reference dataset must point to:

- per-seed raw output directories or chunk roots;
- merged per-seed summary table;
- aggregate summary or merged report;
- protocol audit JSON/text or protocol audit summary;
- v1alpha sidecar manifest/protocol paths when present;
- evaluation output for physical observables;
- run logs;
- chunk merge logs when chunked;
- config snapshots;
- runbook/status note describing the result and caveats.

## Required Modernization Readback Checks

Before accepting a package as a modernization reference:

- check package paths exist from the modernization environment or are intentionally archived;
- check branch/commit/config/seed policy are recorded;
- check `nofb` and `withfb` use matched seed policy unless the reference class explicitly does not require pairing;
- check physical point is `t=0.35`, `L=2`, `nstep=20` for Stage3_4-context-aligned references;
- check method mapping is unambiguous;
- check protocol timing is post-swap measurement/history/label trace, or clearly marked legacy;
- check protocol audit verdict is pass for all included sidecar-enabled runs;
- check merged summaries preserve sidecar/audit columns if sidecars are present;
- check key physical observables and diagnostic counters are summarized;
- check known caveats are documented before the package is used for regression acceptance.

## Registration Output

After readback acceptance, modernization records the package in:

- `state/M6_REFERENCE_PACKAGES.tsv`
- `runbooks/STATUS.md`
- a package-specific readback note under `state/` or `runbooks/`

Registration does not imply the Stage3_4 production comparison is complete. It only means the package can be used by modernization as a behavior-preservation reference.

## Code-Entry Rule

No next-stage source-code modernization that can affect outputs, counters, state propagation, RNG order, solver routing, public schema interpretation, or wrapper behavior should start until at least one accepted modernization reference dataset or explicitly approved substitute baseline exists.
